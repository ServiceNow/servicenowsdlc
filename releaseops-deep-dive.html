Architecture

Two core flows, one pipeline

Assessment flow

Validates a single Deployment Request: Instance Scan → Move to Test → Run ATF → Ready for Deploy. Runs per-DR, whenever you set it going.

Release flow

At the release date, every Deployment Request that has reached Ready for Deployment gets pushed to the final destination together, in one batch.

Architecture

Freeze date vs. release date

Freeze date

The cutoff for reaching Ready for Deployment. Miss it, and the Deployment Request is marked deferred — not blocked. (Robert's preferred name: cutoff date.)

Release date

When the batch push to production actually fires, for every non-deferred Deployment Request.

Deferred is a true/false flag, not a state — a deferred DR can still pass assessment later and ride a different release through the same pipeline.

Architecture

Why dev → test only doesn't work

The assessment flow already moves the app from dev to test. If test is also your "final destination," the release flow has nowhere new to push the payload — it's already there, and the release fails out.

You need at least three instances for ReleaseOps: dev, an assessment target (test, staging, or UAT), and the final destination (e.g. prod).

Architecture

Pause points — the #1 adoption blocker

Every customer has manual steps — change control sign-off, an approval, hypercare setup — that have to happen between automated stages. Pause points are how ReleaseOps accommodates that.
  • ⏸️A pause point is a conditional wait: check for a manually defined Deployment Request Task at that stage; if none exists, continue automatically.
  • 📋Deployment Request Tasks are trackable, assignable records — not verbal agreements — which matters for auditability.
  • 🔀The task's Pipeline field distinguishes an assessment-stage interruption ("am I ready to deploy?") from a release-stage one (post-deploy smoke test, sign-off).
  • 🏷️Task types: Runbook, Test issue, Scan issue, Preview issue.

Walkthrough — Step 1

Build & install the app from the IDE

Studio can't see an app that isn't installed on the instance yet — build and install come first, from the IDE, before Studio ever enters the picture.
  • 🛠️Build the app in your IDE — same Fluent SDK workflow as the build exercise, earlier today.
  • 📥now-sdk build, then now-sdk install — installs it onto the dev instance.
  • 🔎Only after install does the app show up in Studio's Explorer panel — that's where this walkthrough picks up next.

Walkthrough — Step 2

Publish the app to the App Repository

  • 1️⃣Open the app in ServiceNow Studio via the Explorer panel.
  • 2️⃣App Details → Publish. Bump the version — Studio auto-increments it for you.
  • 3️⃣Publish successful — the app is now visible to every other instance in your company.

Walkthrough — Step 3

Find the Update Set publish created

  • 1️⃣Search Local Update Sets on the dev instance.
  • 2️⃣The publish action created one automatically — "Maintenance install version 1.0.1…".
  • 3️⃣Open it — this is the payload your Deployment Request will actually move.
Gotcha: every scoped app also keeps a default "[app] in progress" Update Set open alongside this one — that's standard behavior, not an error. Use the specific maintenance/install version set, not the default.
Walkthrough — Step 4

Create the Release record — the basics

  • 1️⃣On the destination instance: search Releases (ReleaseOps app).
  • 2️⃣New Release record — blank, state Draft.
  • 3️⃣Destination environment: the instance ReleaseOps should ultimately deploy to (here, prod).
Walkthrough — Step 4

Create the Release record — pipeline & timing

  • 1️⃣Pipeline: Sample Release Pipeline (waits for the release date) vs. Sample On Demand Pipeline (pushes as soon as the DR is ready).
  • 2️⃣Freeze date and release date — set close together for a live demo; normally days or weeks apart.
  • 3️⃣Save. Assignment group set to App Engine Admins; state stays Draft until activated.
Walkthrough — Step 5

Promote the Update Set → create a Deployment Request

  • 1️⃣Back on dev: open the update set, click Promote Update Set.
  • 2️⃣Opens a record producer on the destination instance — "Deploy an Update Set."
  • 3️⃣Check "Create new deployment request," link the Release you just made, optionally restrict which ATF suites run.
Walkthrough — Step 6

Activate the Release

  • 1️⃣The Deployment Request won't move to Ready to Assess until its Release is Active.
  • 2️⃣Back on the Release record: Activate Release.
  • 3️⃣State: Active. ReleaseOps has scheduled the freeze-date job behind the scenes.
Walkthrough — Step 7

Ready to Assess → watch it move

  • 1️⃣On the Deployment Request: click Ready to Assess — this is what actually triggers the assessment playbook.
  • 2️⃣State flips to Assessing automatically — no separate approval step.
  • 3️⃣The activity log narrates it live: instance scan completed with 0 findings, then "Started moving updates to…"
Walkthrough — Step 7, continued

Inside Workflow Studio: find the playbook

  • 1️⃣Search "Studio" → Workflow Studio.
  • 2️⃣Filter Playbooks by the ReleaseOps application — four ship out of the box, including Deployment Request Assessment.
  • 3️⃣Open it. Four numbered stages, left to right: Run Instance Scan → Move To Test → Run ATF Tests → Ready for Deploy — next up.
Playbook — Stage 1

Instance Scan

A static policy check on the dev instance. The happy path continues to Move to Test; Failures or Errors branches to a Reconciling task instead.

Playbook — Stage 2

Move to Test

"Test" is a label, not a hard-coded instance — the Integrate Deployment Request activity takes the destination as a configurable input. Here it's literally named "Test," but it could just as easily be Staging or UAT.

Playbook — Stage 3

Run ATF Tests

Two independent sad paths: Failures or Errors, and Low Code Coverage — either one routes to a Reconciling task instead of blocking silently.

Playbook — Stage 4

Ready for Deploy

The finish line for the assessment flow. Getting the Deployment Request to prod from here is the release flow's job, on its own schedule.

Walkthrough — Step 8

Setting up a manual pause point

  • 1️⃣Deployment Request → Deployment Request Tasks. Empty until someone adds one.
  • 2️⃣New task — Type can be Runbook, Test issue, Scan issue, or Preview issue.
Walkthrough — Step 8, continued

Pausing it, and resolving it

  • 1️⃣This task is wired to Playbook stage "Ready for Deploy," waiting on activity "Before Ready for Deployment" — the playbook won't proceed past that point until the task closes.
  • 2️⃣Resolve clears it, and the playbook picks back up — same mechanism whether the sign-off is "ready to deploy?" or a post-deploy smoke test.

Roadmap

What ReleaseOps can't do yet

ATF suite selection from prod

For a net-new app, its ATF suites live in the app and don't exist on prod yet — so you can't pick them from the Deployment Request form there. High-priority roadmap item.

Fixed scripts & data loads

~80% of customers ask for update-set → fixed-script → update-set interleaving. Pause points can wrap a manual step in a tracked task, but ReleaseOps doesn't automate the interleaving itself.

IDE vs. Studio publish

This walkthrough published from Studio; prior bootcamp material only covered the IDE. Open question whether App Repo publish is possible straight from the IDE.

Long-term direction: push customers toward source control as the authoritative source, so one unified package goes to prod instead of several interleaved update sets.

Wrap-up

Deployed to prod

Start to finish: an app built off-instance, published to the App Repo, promoted into a Deployment Request, assessed automatically, and released to production — with a human sign-off exactly where the team wanted one, not everywhere.

  • 🧱Same Update-Set payload the platform has always used — now driven by a playbook instead of a runbook.
  • ⏸️Pause points mean "automatic" doesn't mean "no one signs off" — it means sign-off is a tracked task, not a Slack thread.
  • 🚀The release flow fired on schedule, unattended, for every Deployment Request that was ready.
